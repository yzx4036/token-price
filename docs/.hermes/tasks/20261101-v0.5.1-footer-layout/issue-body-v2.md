## 结论先行：这是需求变更，不是 bug

原记录写的是「页脚总是固定在最前」，实测后确认**当前页脚是正常静态布局**（6 路由 × 2 视口全是 `position: static`，DOM 顺序 `header → main → footer`，无 sticky/fixed）。

用户澄清后的真实需求是：**让页脚浮在内容之上并常驻，这样二维码一直可见。**

因此本条从 bug 改为 feature，验收判据也随之改变。

## 目标

二维码在浏览过程中始终可见，不需要滚到页面底部才能看到。

## 硬约束：不能直接给整个 footer 加 sticky

实测当前 footer 高度与占屏比例：

| 视口 | footer 高度 | 占屏比 | 常驻后剩余可读区 |
|---|---|---|---|
| 桌面 1440x900 | 157px | 17.4% | 743px |
| iPhone X 375x812 | 376px | 46.2% | 436px |
| iPhone SE 375x667 | 376px | 56.3% | 291px |
| 安卓小屏 360x640 | 376px | 58.7% | 264px |

移动端 footer 是竖排（免责声明 227px + 二维码 88px + 汇率行全堆叠），整块 sticky 会吃掉一半以上屏幕，远超可接受范围。

**并且移动端常驻二维码本身无效**：用户在手机上看页面时，无法用同一台手机扫描自己屏幕上的二维码。

## 可选项（待定）

### A. 整个页脚 sticky bottom（用户原话）
- 桌面 17.4% / 移动 56%
- 违背移动端可用性下限（正文可读区不足 300px）
- 不建议采用

### B. 只让二维码浮起（推荐）
- 页脚保持在文档流末尾不动（免责/汇率仍在那里）
- 另起一个独立悬浮组件，只在桌面（>=1024px）显示：右下角固定卡片，二维码 112px + 一句关注理由 + 关闭按钮
- 移动端不常驻（扫码无效），二维码仍出现在页脚 + 数据来源页
- 代价：桌面约 12.4% 屏高，可关闭

### C. 桌面整页脚 sticky + 移动端只浮二维码
- 桌面保留「页脚常驻」的原意
- 移动端降级为不常驻
- 代价：桌面 17.4%，且整块免责声明常驻会干扰阅读

### D. 右下角圆形按钮，点击展开
- 常驻只有 48-56px 圆钮（桌面移动都适用）
- 点击后展开二维码卡片
- 代价：多一次点击；但占地最小，也不遮挡内容

## 验收判据（按选定方案细化）

- [ ] 常驻元素不遮挡正文：滚动到任意位置，正文表格没有被浮层盖住（或浮层可关闭/可让位）
- [ ] 移动端剩余可读区 >= 60% 视口
- [ ] 二维码图片可扫（视觉复检 + 实际扫码）
- [ ] 关闭状态要记住（localStorage 记一次），避免反复打扰
- [ ] 浮层不参与 SEO 抓取重复计数：二维码区块在正文里已有一份，浮层用 aria-hidden 或不重复输出图片
- [ ] 加入门禁：断言常驻浮层高度不超过视口 20%
- [ ] 6 路由 x 4 视口复测，无横向溢出、无内容遮挡

## 与 issue #9 的关系

#9 里有一条「水合后跳变」的问题。浮层若依赖客户端 JS 渲染，必须避免水合前后 DOM 不一致——用构建期常量控制显隐，与二维码现有做法（`__HAS_WECHAT_QR__`）保持一致。
