## 本次实测结论（先纠正两条前提）

### 验收标准 4「体积偏大」——前提不成立，无需优化

issue 里写的 364KB 是**未压缩** HTML。线上实际传输：

| 文件 | 原始 | gzip | 压缩率 | 线上实测 |
|---|---|---|---|---|
| `api-pricing/index.html` | 370,462 B | 20,275 B | **5.5%** | `Content-Encoding: gzip`、`Content-Length: 22314` |
| `plans/index.html` | 120,639 B | 14,717 B | 12.2% | — |

真实下载量是 22KB。而且详情折叠区占 HTML 的 51.9%（161,767 / 311,745 B），把它从 SSR 摘掉会同时丢掉两样东西：①禁用 JS 的读者点不开 `<details>`（`<details>` 是原生 HTML，本来不需要 JS）；②「用途限制」「可用模型」这些长尾搜索词的正文。**这与本里程碑 v0.9.0「静态可索引」的目标直接冲突**，所以不做。

### 验收标准 2「禁用 JS 时桌面端可读」——已达标

关掉 JS 实测桌面 1440×900：`.price-cards` 已是 **3 列网格**（每卡 450×305），不是单列巨卡。`global.css` 里 `@media (min-width: 1024px)` 早就设了 `repeat(3, ...)`。可读、无横向溢出。

### 验收标准 3「卡片与表格不同时存在」——已达标，并已加门禁锁死

线上实测：桌面 `.price-card`=0 / `table`=1；手机 `.price-card`=178 / `table`=0。`v-if` 分支保证互斥。

## 验收标准 1「桌面水合不跳变」——量化了，但没修，原因如下

实测桌面 1440×900：

| 阶段 | 结构 | 页面总高 |
|---|---|---|
| 水合前（SSR，禁 JS） | 3 列卡片 | **6,922 px** |
| 水合后 | 表格 | **4,168 px** |

差 **−2,754 px（−40%）**。根因是密度差：卡片 305px 一张，表格行 57px 一行。

**要消除它只有两条路，都不该在本条里做：**

1. **两套结构都进 DOM，CSS 按断点显隐** —— 能彻底消除跳变，但 DOM 从 8,749 节点涨到约 15,000。这个页面本来就已经是 Lighthouse「DOM 过大」的红灯（阈值 1400，现在 6 倍），再翻倍是拿一个体验问题换一个更实的性能问题。
2. **单一结构＝表格，移动端用 CSS 重排成卡片** —— 架构上最干净，但等于把现在这套调好的移动端卡片（评分 chip、溯源徽章、折叠区）整体换成「带 data-label 的重排表格行」。这是可见的产品改版，不是修 bug，需要你拍板。

issue 里原本也写了「明确不做：不为 SSR 强行输出表格 DOM（那会让移动端首帧是宽表，反而要横滚）」—— 顾虑是横滚。如果走路线 2，`display:block` 重排后不会横滚，那个顾虑不成立；但移动端视觉会变。

## 本次已落地：P8 门禁（验收标准 5）

`scripts/verify-static-build.mjs` 新增 P8，三条判据都防「构建 rc=0 但页面已经坏了」：

| 判据 | 防的是什么 |
|---|---|
| 卡片与表格不得同时出现 | 有人把 `v-if` 改成并列渲染，同一份数据两套结构进 DOM，读屏重复播报 |
| 渲染行数 == 页面自述「共 N 条/档」 | SSR 少渲染几行，但摘要仍显示旧数字——页面看起来正常，实际缺数据 |
| 渲染行数 ≥ 源数据条数 | merge / 过滤把数据吃掉，却仍然「通过」 |

真实产物实测：`P8 API：卡片 178 张，与自述条数一致`、`P8 套餐：卡片 55 张，与自述条数一致`。

门禁本身也按项目纪律造反例。新增 5 条反例测试（`tests/verify-static-build.test.ts`，门禁测试 23 → 28）：

- 卡片与表格并存 → 抓红
- 自述 99 条实际 3 张 → 抓红
- 源数据 5 条只渲染 2 张 → 抓红
- 既无卡片也无表格 → 抓红
- 表格结构下 2 行数据 + 1 行表头，自述 2 条 → 必须通过（验证扣表头的逻辑没写成 off-by-one）

源数据目录改为 `--root` 可配置，测试用 3 条 / 2 条的夹具，不绑真实数据条数 —— 否则数据一涨测试就假红。
